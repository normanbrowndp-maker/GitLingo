# Supabase Auth в GitLingo

Игровой прогресс остаётся общим для браузера и не разделяется по аккаунтам. После определения Auth-сессии страница аккаунта один раз читает собственную строку `user_progress`; пользователь также может запустить проверку вручную. Запись выполняется только после явного сравнения и подтверждения. Логин, выход, уроки и просмотр профиля не отправляют игровой прогресс.

## Файлы

- Публичные параметры проекта задаются в `js/supabase-config.js`. Поля `projectUrl` и `publishableKey` оставлены пустыми до локальной настройки.
- Auth API, PKCE callback, сессия, профиль и обработка событий находятся в `js/auth.js`; интерфейс — в `auth.html` и `js/auth-page.js`.
- Официальный локальный browser bundle `@supabase/supabase-js` версии `2.118.0` подключается как обычный script из `assets/vendor/supabase-js-2.118.0.js`. Источник, точная версия, проверенная целостность архива и MIT-лицензия указаны в `assets/vendor/README.md` и `assets/vendor/SUPABASE_JS_LICENSE.txt`. Во время работы CDN не используется.
- `tools/serve-local.ps1` запускает простой статический сервер на loopback, порт `8000`. Из PowerShell в корне проекта запустите `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\serve-local.ps1`, затем откройте `http://localhost:8000/`. Остановите сервер через Ctrl+C. Он обслуживает только HTML/CSS/JS и изображения из проекта, не показывает `.git` и не принимает запросы на запись. Через `file://` гостевой режим работает, но Auth-вызовы не запускаются.

В `js/supabase-config.js` укажите только корневой URL вида `https://PROJECT_REF.supabase.co` и публичный `sb_publishable_...` key. Не добавляйте `/auth/v1`, `/rest/v1`, `secret`, `service_role`, JWT secret или пароль базы. Если поля пусты, приложение остаётся гостевым и показывает, что подключение не настроено.

Публичный ключ доступен посетителю сайта и не является секретом; права всё равно ограничивает сервер. Secret/service-role key и пароль базы нельзя помещать в клиентский файл, даже если назвать его `config.js` или `.env`. В проекте этого этапа нет реальных ключей.

## Настройки Dashboard

Создайте отдельный тестовый Supabase-проект и используйте уже подготовленную миграцию `supabase/migrations/20261027090000_prepare_accounts.sql`. Облачная копия — ручное сохранение с подтверждением, а не полная синхронизация.

В Authentication включите email/password signup и оставьте включённым подтверждение email. Для hosted Supabase настройка подтверждения включена по умолчанию, но проверьте её явно. Email template подтверждения должен вести на `{{ .ConfirmationURL }}`; Auth после проверки возвращает пользователя на переданный приложением `emailRedirectTo`. Не отключайте подтверждение для обхода тестовых ограничений почты.

В Authentication → URL Configuration:

| Поле | Локальная проверка | Опубликованный сайт |
|---|---|---|
| Site URL | `http://localhost:8000/` | `<ПОДТВЕРЖДЁННЫЙ_HTTPS_ORIGIN>/<PROJECT_PATH>/` |
| Redirect URLs | `http://localhost:8000/auth.html` | `<ПОДТВЕРЖДЁННЫЙ_HTTPS_ORIGIN>/<PROJECT_PATH>/auth.html` |
| Email confirmation return | `http://localhost:8000/auth.html` | `<ПОДТВЕРЖДЁННЫЙ_HTTPS_ORIGIN>/<PROJECT_PATH>/auth.html` |
| Password recovery return | `http://localhost:8000/auth.html` | `<ПОДТВЕРЖДЁННЫЙ_HTTPS_ORIGIN>/<PROJECT_PATH>/auth.html` |

В Dashboard задаются `Site URL` и разрешённые `Redirect URLs`. Строки возврата подтверждения и восстановления выше показывают адрес `auth.html`, который приложение передаёт SDK для обоих писем; добавьте этот точный адрес в разрешённые Redirect URLs.

Проект GitHub Pages обычно размещается внутри пути репозитория. Проверьте фактический HTTPS URL и project path в настройках GitHub Pages и замените плейсхолдеры; production-адрес здесь намеренно не выдуман. Не добавляйте широкий production wildcard, если достаточно точного callback URL. Локальная команда выше обслуживает корень проекта на порту `8000`, поэтому локальный callback — `/auth.html`.

Приложение формирует callback через URL API от текущей страницы и сохраняет относительный путь проекта. Оно не принимает произвольный redirect из query-параметров.

## Потоки и сессия

- Регистрация вызывает официальный `auth.signUp({ email, password, options: { emailRedirectTo } })`. Email обрезается по краям, пароль не меняется. Подтверждение пароля сверяется точно. При включённом подтверждении отсутствие `session` означает, что пользователь ещё не вошёл; интерфейс нейтрально предлагает проверить почту и не сообщает, зарегистрирован ли адрес.
- Вход использует `signInWithPassword`. Неверные данные отображаются общим сообщением без подтверждения существования email.
- Клиент создаётся один раз на странице с `flowType: "pkce"`, `detectSessionInUrl`, `persistSession` и `autoRefreshToken`. SDK обрабатывает callback и обновляет токен. Callback-код и ошибки удаляются из адреса только после события SDK; значения токенов не выводятся и не копируются приложением.
- PKCE verifier хранится SDK в этом браузере. Ссылка подтверждения или восстановления должна быть открыта в том же браузере и на том же устройстве, где была начата операция. Открытие в другом браузере/устройстве может завершиться ошибкой verifier; в таком случае запросите новое письмо.
- Browser SDK сохраняет сессию в browser localStorage. Это удобно для восстановления входа после перезагрузки, но не является защищённым серверным хранилищем: пользователь и скрипты с доступом к origin могут просматривать данные браузера. Приложение не делает дополнительных копий токенов. Выход вызывает `signOut({ scope: "local" })` и не очищает всё хранилище или ключи игры.
- Восстановление вызывает `resetPasswordForEmail` с тем же callback URL. Ответ нейтрален относительно существования адреса. Форма нового пароля показывается только после события `PASSWORD_RECOVERY` от SDK при валидной recovery-сессии; query `mode=recovery` не открывает её. После `updateUser({ password })` пользователь остаётся в текущей сессии.
- Если конфигурации нет, она неверна или страница открыта через `file://`, Auth-запросы не запускаются. Вход в уроки остаётся необязательным.

## Отображаемое имя профиля

После восстановления обычной сессии страница `auth.html` загружает `public.profiles` текущего пользователя и один раз проверяет его `public.user_progress`. Идентификатор берётся только из актуальной Auth-сессии; форма, URL и параметры запроса не могут выбирать владельца. Отсутствующая строка профиля создаётся только по кнопке «Сохранить». Существующее имя можно изменить или отменить изменение. Игровая копия записывается только отдельным действием после просмотра сравнения и повторного подтверждения.

Имя — отображаемое `display_name`, не логин и не уникальный идентификатор. Email остаётся способом входа. При сохранении удаляются крайние обычные пробелы; разрешена длина 1–40 Unicode-кодовых точек, включая кириллицу, латиницу, пробелы внутри и дефисы. Атрибут HTML `maxlength=80` оставляет место для 40 символов вне BMP, а проверка приложения считает именно Unicode-кодовые точки, как `char_length` в PostgreSQL. Клиент не отправляет `created_at`/`updated_at`: время выставляет база. Создание использует только `id` и `display_name`; изменение — только `display_name` и фильтр текущего `id`. При конфликте создания приложение перечитывает свою строку, не перезаписывая её автоматически; введённое имя остаётся в форме для явного повторного сохранения.

Профиль и сведения об облачной копии не кэшируются в localStorage и очищаются из интерфейса при выходе или смене пользователя. Ошибка чтения не отменяет вход. Восстановление пароля сначала показывает только форму нового пароля. Облачный снимок никогда не загружается в игру, автоматически не отправляется и не объединяется с локальными данными. Локальный прогресс остаётся общим для этого браузера. Клиентское хранение XP не защищено от накрутки; облачная копия не заменяет резервное копирование базы.

## Ручная проверка

1. В отдельном тестовом проекте настройте URL выше и подтвердите email/password.
2. Заполните только Project URL и publishable key в локальной копии `js/supabase-config.js`. Не присылайте эти значения в чат. Убедитесь, что не добавили ключ в изменённый файл перед коммитом, если репозиторий не должен публиковать конфигурацию конкретного проекта.
3. Запустите локальный сервер и проверьте гостевой режим с пустой конфигурацией. Затем настройте параметры и проверьте регистрацию, подтверждение письма, вход, неверный пароль, reload с активной сессией и локальный выход.
4. Проверьте быстрые повторные нажатия, отключение сети и повтор после восстановления. Убедитесь, что сообщение о частоте запросов не вызывает автоматических повторов.
5. Запросите восстановление, откройте письмо в том же браузере, установите новый пароль. Отдельно проверьте истёкшую/использованную ссылку и сценарий открытия в другом браузере.
6. Проверьте профиль и облачную копию на отдельных тестовых аккаунтах. Не используйте аккаунт с синтетической строкой `{v: 1, xp: 10}` для сохранения: она должна показываться как неподдерживаемая и оставаться нетронутой. Для чистого тестового аккаунта проверьте отсутствие строки, первую запись с подтверждением, повторное сохранение с ростом `revision`, перезагрузку и повторное чтение. В двух вкладках проверьте revision-конфликт; повторите с быстрым двойным кликом. Отключите сеть во время проверки и записи, попробуйте вручную после восстановления. Во время запроса выйдите или смените аккаунт; проверьте, что поздний ответ не появляется в новом аккаунте. Измените локальный прогресс после сравнения и убедитесь, что требуется новое подтверждение. В копии тестового браузерного профиля проверьте повреждённый JSON и будущую локальную версию: запись должна блокироваться, исходные строки и backup не должны меняться. На отдельном тестовом аккаунте проверьте более новую и синтетическую неполную облачную версию; не стирайте её. Убедитесь, что вход и уроки сами не записывают строку, `mega-state`, тема, последний результат и backup-копии не меняются облачными действиями, а профиль и восстановление пароля работают.
7. Проверьте экран на 360, 768 и 1280px в светлой и тёмной теме, клавиатурную навигацию и отсутствие горизонтальной прокрутки. На опубликованном HTTPS сайте настройте и проверьте production callback отдельно.

Ограничения тестовой доставки email зависят от настроек Supabase: встроенная почта на hosted-проекте ограничена и не предназначена для production. Проверьте текущие ограничения проекта и настройте собственный SMTP до публичного запуска. Доставка письма не гарантируется мгновенно.

Автоматической загрузки и восстановления нет. Строка `user_progress`, включая синтетическую тестовую строку, не загружается в игру и не применяется для локального состояния. Клиентская запись не подтверждает честность XP или игровых результатов; для тестов и эксплуатации используйте отдельные аккаунты и сохраните резервные копии самой базы.
