Документ задаёт направление развития курса. Статус уже выполненной части и точечные уточнения схемы зафиксированы в разделе «Реализация первого раздела».

## 1. Аудит текущего курса

Состояние проверено по `js/data/lessons.js`, `GitLingo.validateBank()`, `js/learn.js`, `js/lesson.js`, `js/task-checks.js`, `js/review.js`, `js/results.js`, `js/storage.js`, `STORAGE.md`, `GAMEPLAY.md` и миграции Supabase. Точных дубликатов текста вопросов в банке нет. Есть повторы проверяемых действий: это полезно для извлечения из памяти, если меняется контекст и требуется объяснить выбор; сейчас большая часть повторов — та же команда в почти той же формулировке. Например, повтор `git add` полезен, когда в первом задании выбирается файл для индекса, а в следующем по выводу `git status` нужно понять, какой файл ещё не добавлен. Повтор `git branch` полезен, если сначала пользователь читает список, а затем выбирает безопасное действие для существующей ветки. Повтор PR/push полезен в сценарии «локальный commit → отправка ветки → PR», а не в двух почти одинаковых вопросах.

`GitLingo.validateBank()` проверяет наличие целей, объяснений, коротких подсказок, 2–4 карточек теории, базовую структуру вариантов, блоков builder и четырёх matching-пар. Она не проверяет смысловое соответствие ответа и объяснения, наличие теории для каждого тестового навыка, уникальность вопросов, среду команд или минимальную длину тестов для уроков 2–5. Комментарий валидатора прямо называет уроки 2–5 короткими заглушками; правило минимальной длины теста сейчас применяется только к уроку 1.

Все текущие вопросы имеют `explain` и `hint`, однако их наличие не доказывает корректность объяснения. Например, объяснение тестового `git diff` говорит лишь о сравнении изменённых версий файлов, не уточняя ключевую границу: обычный `git diff` сравнивает рабочее дерево с индексом и не показывает staged-изменения (для них нужен `git diff --staged`). В первую очередь перепроверить также упрощённое описание `pull`, окружение для `clear`/`Tab`/`Ctrl+C`, тестовые Git-команды внутри урока о терминале и различие Git/GitHub в уроке 5. Figma и VS Code уже помечены полем `app`; команды уроков 1–5 обычно не имеют такого поля среды.

### Текущая механика и технические ограничения

- Уровень знаний хранится в `state.profile.level` (`Ничего`, `Немного`, `Уверенно`). Он меняет вход в урок: для «Немного» доступен пропуск теории, для «Уверенно» — быстрый вход к теории/тесту. Он **не меняет подсказки**: в практике у всех есть одна кнопка, в тесте она скрыта.
- При 0 сердец обычный путь принудительно переводит практику в свободный режим: ошибки не снимают сердца, XP и тест не засчитываются. Новая попытка теста блокируется также в `beginTest()`. Бонусы доступны отдельно; при 0 сердец проходят как свободная практика и не получают первое бонусное завершение/XP. Существующий явный маршрут восстановления сердец остаётся единственным; таймеры и новые награды не добавлять.
- Разбор ошибок использует текущие типы `choice`, `builder`, `hotkeys`, `matching`; неправильный ответ остаётся в очереди, правильный закрывает версию записи и возвращает фактически доступное сердце. Новые типы должны поддерживаться и основным рендерером, и проверкой, и `review.html`.
- `state.v` и `user_progress.schema_version` сейчас равны `1`. Локальное состояние хранит `lessons` по ID `1..5`, `bonuses` по `b1/b2`, сердца и ошибки. Облачный снимок проверяет полную текущую структуру. Существующий Supabase check связывает `schema_version` со значением `state.v`; SQL/RLS в рамках этого плана не меняются.
- Ошибка привязана к `unitKind`, `unitId`, `phase`, позиции вопроса и отпечатку его структуры. Вставка вопроса в середину, изменение вопроса или перестановка индексов может сделать старую запись неактуальной. `results.js` выбирает следующий урок по `current ID + 1`, `learn.js` ищет предыдущий по `id - 1`, `storage.js` жёстко задаёт набор уроков `[1,2,3,4,5]` и бонусов `[b1,b2]`, а `GitLingo.validateBank()` имеет специальное условие для урока 1. Карта сейчас рисует одну вертикальную линию по порядку массива, а бонусы показывает отдельной секцией, не боковыми входами.

## 2. Предлагаемая последовательность курса

Среда примеров по умолчанию — **Git Bash из Git for Windows**. В карточке среды это указано явно. Если понадобится PowerShell-вариант, он показывается отдельной подписанной строкой; `pwd`, `ls`, `clear`, `touch` и redirection не объявляются универсальными shell-командами. Figma/VS Code — отдельные приложения; для VS Code в первом расширении указывать Windows/Linux (`Ctrl`), а macOS-вариант подписывать `Cmd` либо не проверять.

При необходимости старые короткие уроки остаются доступными как прежний материал/результаты, но их completion не закрывает новые узлы.

Практические примеры используют вымышленные небольшие репозитории и фиксированные выводы команд. Они учат рассуждать о состоянии, но не исполняют пользовательский shell, не обращаются к GitHub и не отправляют файлы по сети.

## 4. Спецификация новой карты

### Модель графа

Каталог карты задаётся явными узлами с неизменяемыми `nodeId`, `kind`, ссылкой на содержимое и списком `requires`. Например, `course-terminal-study`, `course-terminal-practice`, `course-terminal-check`. Следующий раздел определяется графом зависимостей, не `id + 1`. Данные уроков и бонусов хранятся один раз; узлы только ссылаются на них. Отдельные node ID нужны для теории, практики и контроля без клонирования заданий.

| Тип узла | Оформление и запуск | Открытие | Завершение | Повтор | При 0 сердцах |
| --- | --- | --- | --- | --- | --- |
| Обучение / теория | Сине-фиолетовый круг с SVG-книгой/терминалом и явной подписью «Теория»; открывает вводную и карточки теории выбранного раздела. | Первое обучение открыто; следующие узлы — по `requires` предыдущего раздела. Опциональные справочные карточки доступны без прохождения теста. | Зафиксировано, что обязательные карточки просмотрены; это не считается сдачей контроля. | Открывается повторно, без XP и штрафов. | Доступно. |
| Самостоятельная практика | Золотой узел с отдельной SVG-иконкой упражнения и текстом «Практика». | После обязательной теории данного раздела. | После обработки всех заданий узла; ошибки сохраняются в текущей очереди по существующим правилам. Практика сама не сдает тест и не разблокирует следующий раздел. | Первый оцениваемый проход использует текущие правила начисления; свободные повторы после прохождения и при нуле сердец не списывают жизни и не выдают обычную повторную XP. | Доступна как свободная практика: без потери сердец, XP и тестового зачёта, согласно текущему режиму. |
| Контроль / тест | Золотой узел с отличной от практики SVG-иконкой проверки и подписью «Тест». Цвет не является единственным отличием. | После практики и только при `hearts > 0`; условие проверяется при запуске, не только на карте. | Сдан при существующем `PASS_RATIO` (80%); именно подтверждённый проход открывает следующий раздел. Ошибки, неотвеченные вопросы и прерванная попытка остаются разными статусами. | Разрешён при наличии сердца; статус уже сданного узла не откатывается. Существующая логика XP при повторном успешном тесте должна быть отдельно проверена до изменения; карта не добавляет награду за факт повторного открытия. | Не запускается. Рядом показывается объяснение и переход к работе над ошибками/существующему восстановлению сердец. |
| Бонус Figma / VS Code | Боковой узел за пределами основной дорожки: прежний собственный акцент и существующая `icon-figma`/`icon-vscode`. Подпись сообщает название приложения. | Не требует и не открывает основной раздел. | Использует существующее состояние того же бонуса `b1`/`b2`, без второй копии контента или прогресса. | После первого получения награда не дублируется по текущему правилу `completeBonus`; просмотр и свободный повтор остаются возможны. | Открывается как свободная практика без XP и отметки первого успешного бонуса, как сейчас. |

На широкой карте узлы идут извилистой вертикальной дорожкой с чередованием текста по сторонам; линия между узлами тонкая и не похожа на шкалу ошибки. На мобильном дорожка становится одноколоночной, подпись всегда рядом с узлом, интерактивные зоны остаются полными и не требуют точного попадания. Пройденные отрезки отражают только сохранённое состояние. Текущий узел отмечается мягкой рамкой/ореолом без постоянной анимации. Заблокированные узлы имеют нейтральную поверхность и объяснение условия, не красный цвет.

Для будущих переходов достаточно короткой реакции на нажатие, появления узла и заполнения участка пути. В `prefers-reduced-motion` перемещение/масштаб отключаются; постоянного движения нет. Теория, практика и тест различаются текстом, доступным именем и формой/иконкой, а не только цветом. Все действия — семантические ссылки/кнопки с клавиатурным фокусом.

## 5. Три новых формата заданий

Все три формата используют общую функцию проверки в `js/task-checks.js`, явную структуру ответа, данные банка без DOM и без исполнения команд. Перед включением в ошибки повтора тип должен быть разрешён в `storage.js`, нормализоваться в короткое безопасное описание ответа и отображаться в `review.js` из актуального банка. Вопросы получают неизменяемый `questionId`; изменение смысла требует нового ID.

### 5.1 Прочитать вывод команды (`output-reading`)

- **Навык:** сделать вывод о состоянии репозитория по нескольким строкам, а не угадать команду.
- **Пример:** Git Bash, `git status --short` вывел ` M README.md` и `?? notes.txt`. Вопрос: «Какое состояние у каждого файла?» Правильный ответ: `README.md` изменён только в рабочем дереве; `notes.txt` не отслеживается; индекс пуст.
- **Проверка:** ответ — набор перечислений `{path, indexState, worktreeState}`. Проверить допустимые статусы и точное соответствие ожидаемых путей/состояний; порядок строк и порядок выбора не значимы. В HTML вывод показывать в `<pre>` с сохранением пробелов, текст — через `textContent`.
- **Управление:** указать состояние через кнопки/checkbox с видимым текстом; Tab/Shift+Tab и Space работают без drag-and-drop.
- **Review:** повторно показать тот же вывод и попросить независимо отметить состояния; неправильная попытка показывает объяснение и не закрывает очередь. В запись ошибки класть только выбранные статусы, не весь DOM.
- **Поля банка:** `id`, `type`, `question`, `environment`, `command`, `output`, `records`, `answer`, `explain`, `hint`.
- **`GitLingo.validateBank()`:** уникальный ID; среда/команда/вывод непустые; строки вывода ограничены по размеру; каждый ожидаемый путь существует ровно один раз; значения статусов входят в whitelist; ответ покрывает ожидаемые записи без дубликатов.

### 5.2 Найти и исправить ошибку (`diagnose-fix`)

- **Навык:** определить причину неудачного действия по контексту и исправить ровно одну ошибку.
- **Пример:** «Ветка `docs` уже существует. Нужно на неё перейти». Предложенная команда: `git switch -c docs`. Правильное исправление: `git switch docs`; `-c` пытается создать ветку повторно.
- **Проверка:** банк перечисляет разрешённые варианты исправления, а проверка сравнивает выбранный `fixId`; для ввода команды нормализуются только пробелы вокруг аргументов, не кавычки и не флаги. Никакая команда не исполняется. Объяснение обязательно называет причину и возможное последствие.
- **Управление:** кнопки вариантов либо текстовое поле с кнопкой проверки; работает клавиатурой. Не требовать перетаскивания.
- **Review:** показать исходное состояние без раскрытого исправления; самостоятельный повтор проверяет тот же `fixId`. Неверный ответ раскрывает решение только после фиксации ошибки.
- **Поля банка:** `id`, `type`, `question`, `environment`, `context`, `proposal`, `fixes: [{id, label, command?}]`, `answer`, `explain`, `hint`.
- **`GitLingo.validateBank()`:** не менее двух уникальных исправлений; ответ ссылается на один существующий ID; контекст и предложение заданы; команды используют только заранее разрешённый учебный формат; объяснение не пустое. Разрушительные команды и неопределённые исправления отклоняются.

### 5.3 Расположить действия по порядку (`sequence`)

- **Навык:** выполнить правильную последовательность с учётом зависимости действий.
- **Пример:** «Изменён только `README.md`. Подготовь его и создай коммит». Правильный порядок: проверить состояние (`status`), добавить README (`add README.md`), проверить индекс (`diff --staged`), создать коммит (`commit -m ...`).
- **Проверка:** банк задаёт список уникальных ID шагов и правильный порядок; сравнивается последовательность ID, не локализованные подписи. Если в будущем допускаются альтернативы, они явно задаются допустимыми частичными ограничениями, а не нестрогим подсчётом совпадений.
- **Управление:** у каждого шага есть кнопки «Выше»/«Ниже» с `aria-label`; стрелки перемещают только сфокусированный шаг внутри списка, Space/Enter активируют кнопки. Drag-and-drop не требуется.
- **Review:** восстановить исходный перемешанный список и дать новую самостоятельную расстановку. Неправильная расстановка не повторяется бесконечно и не закрывает запись.
- **Поля банка:** `id`, `type`, `question`, `environment`, `steps: [{id, label}]`, `answer: [stepId]`, `explain`, `hint`.
- **`GitLingo.validateBank()`:** 3–8 шагов; ID уникальны; ответ содержит каждый существующий ID ровно один раз; ссылки на неизвестные шаги запрещены; подсказка не выдаёт весь порядок.

В первой версии внедрять только `output-reading`: он лучше всего закрывает пробел между чтением реального вывода и угадыванием команды. `diagnose-fix` и `sequence` добавить после совместимости review/хранилища, каждый отдельным небольшим этапом. Три новых типа — верхний предел этого плана, не требование одновременно реализовать все.

### Связанная мини-практика

Позже связать 3–5 экранов одной симулируемой историей, например «подготовить README»: посмотреть status → выбрать единственный нужный файл → прочитать staged diff → собрать commit → оценить конечную историю. Между шагами передаётся только минимальное учебное состояние с выбранными вариантами. Пользователь видит последствия, но браузер не запускает shell, не меняет файлы и не обращается к удалённому репозиторию. На первом содержательном этапе хватит одного короткого сценария внутри раздела терминала/рабочей папки, не отдельного sandbox-терминала.

## 6. Правила подсказок и экрана урока

Подсказка — короткий способ направить рассуждение, а не готовая команда или ответ. Основная типографика остаётся той же читаемой, что и у текста задания; подсказка помещается под карточкой, переносится на мобильном и не накладывается поверх ответа.

| Уровень | Поведение в первых разделах |
| --- | --- |
| `Ничего` | Подсказка видна под карточкой сразу. Это короткое направление вроде «Сначала посмотри, в какой папке находишься», без названия нужного варианта или готовой строки команды. |
| `Немного` | Под подсказкой есть кнопка «Показать подсказку»; текст скрыт по умолчанию. Состояние раскрытия объявляется через `aria-expanded`. |
| `Уверенно` | Автоматическая подсказка не показывается; та же доступная кнопка позволяет открыть помощь. |

Уровень выбирает объём помощи, но не меняет правильность проверки, XP, сердца, проходной порог или критерий открытия следующего раздела. Подсказки проходят редакционную проверку: нельзя просто повторить формулировку правильного ответа. В тесте нет вопросных подсказок ни для одного уровня. Допустимы обычная инструкция к формату и нейтральные средства доступности; открыть теорию можно до теста, но решение конкретного тестового вопроса не раскрывается незаметно. Если тест прерван, результат явно отмечает неотвеченные вопросы.

В будущей оболочке не показывать постоянно полную полоску «Введение / Теория / Задания / Тест». В компактной шапке рядом с названием показывать только текущий статус, например «Теория · карточка 2 из 3» или «Практика · вопрос 4 из 8». Введение и теоретические карточки сохраняются как содержимое и остаются доступны согласно уровню и правилам узла.

## 7. Совместимость, состояние и риски

1. **Не перенумеровывать старое.** Числовые уроки `1..5`, бонусы `b1/b2`, result links и существующие сохранённые поля остаются валидными. Новая последовательность хранится в отдельном явном графе со стабильными строковыми `nodeId`; `id` содержимого никогда не определяет порядок.
2. **Не признавать короткую заглушку освоением нового курса.** Старые `lessons[id].completed`, `testPassed` и `bestAccuracy` остаются историческими результатами. Новая дорожка читает отдельное необязательное поле `courseProgress` с прогрессом по `nodeId`. При первом открытии отсутствующее поле означает пустой прогресс нового курса, а не копию старых отметок. Не стирать и не пересчитывать `xp`, `hearts`, `streak`, бонусы и результаты.
3. **Существующая схема ошибок.** Сохранить вычисление ID старых вопросов и порядок/структуру legacy-банка, чтобы уже записанные ошибки находили прежние задания. Новые задания получают постоянный явный `id`, независимый от индекса. Вставка/перемещение старого вопроса запрещены без таблицы совместимости. При несовместимом изменении старый вопрос показывается как устаревшая запись: не запускается и не даёт сердце; пользователь может убрать его штатным действием.
4. **Новые типы ответов.** Расширять whitelist и безопасную нормализацию в `storage.js` только под точные типы ответа. Не сохранять DOM, HTML, функции, копию банка или произвольный текст без ограничений. Основной урок и review используют одну проверку. Для старых записей продолжают работать старые варианты `answer`.
5. **Миграция локального состояния.** `courseProgress` сначала проектировать как необязательное additive-поле: валидная версия 1 без него трактуется как пустой новый трек; читать её не означает автоматически записать миграцию. При первом реальном прогрессе записывается только новое поле вместе с существующим state через центральный storage API. Если потребуется разрушительное изменение или обязательное новое поле, остановиться, повысить версию и применить действующий механизм точного `mega-state-backup-v1` до перезаписи. Сброс и пересчёт XP запрещены.
6. **Старые облачные копии.** Полные `schema_version: 1` копии без `courseProgress` остаются допустимыми; отсутствие новой необязательной дорожки не делает их повреждёнными. Проверка старого снимка не создаёт локальный backup и не восстанавливает облако. Новые данные отправляются только существующим ручным подтверждением. Перед любым повышением `schema_version` отдельно проверить текущий клиентский валидатор и constraint `state.v = schema_version`; не менять SQL/RLS автоматически в рамках реализации карты.
7. **Повторные награды.** Состояние узла само по себе не выдаёт XP. Успешный контроль сохраняет лучший результат/статус один раз по текущим правилам, а повтор использует существующий путь урока; отдельная регрессия проверяет фактическую XP-награду повторной сдачи. Награды за исправления остаются под атомарной защитой `resolveReviewQuestion`; повторная вкладка не может повторно засчитать запись.
8. **Сердца и блокировка.** Новый граф не меняет лимит 5, существующее восстановление, свободную практику при нуле или запрет нового теста без сердца. Условие теста проверяется также в обработчике запуска. Если при нуле нет очереди ошибок, показывается существующее действие явного восстановления; новые таймеры, платежи и награды не появляются.

### Предпосылки кода для порядка/узлов

Перед переносом карты убрать зависимость нового графа от `currentId ± 1`: `learn.js` рисует порядок из массива и ищет предыдущий арифметически; `results.js` предлагает `lessonId + 1`; `storage.js` содержит `lessonIds = [1,2,3,4,5]`; валидатор имеет специальный минимум только для `id === 1`. `lesson.js` ищет содержимое по legacy ID, считает один unit полноценным сценарием и выставляет теорию/практику/тест как общий путь. Новая карта должна направлять на конкретный `nodeId`/phase, не добавлять искусственные дубликаты unit.

До первой реализации нужны проверки старого полноценного local state, состояния с очередью ошибок и старого облачного снимка без нового поля. Реальное облако и реальные пользовательские данные не используются в фикстурах.

## 8. Очередь этапов реализации

1. **Контракт курса и графа.** Описать явные `nodeId`, `requires`, ссылки на содержимое и цели; валидатор проверяет отсутствие циклов, дубликатов ID, неизвестных зависимостей и недоступных узлов. Зафиксировать legacy ID и контрольные фикстуры v1 до изменений.
2. **Один полный раздел: «Терминал и файловые пути».** Реализовать законченное введение/теорию, практику и тест на Git Bash, понятные примеры, поэтапную помощь и проверяемый критерий. Включить один `output-reading` после общего рендера/проверки/review. Добавить узлы теории, практики и контроля. Для первого запуска дать конечный набор качественных вопросов (ориентир: 8 заданий практики и 5 контрольных, не сотни вариантов) и проверить при 0/1/5 сердцах, выход, review и мобильную клавиатурную доступность.
3. **Совместимость и сохранение результата первого раздела.** Добавить отдельное необязательное `courseProgress`, legacy fallback для ошибок, проверки экспорта и чтения полного cloud v1 без этого поля. Существующие completion не переносятся в новый трек. Проверить повторный запуск и подтверждённые изменения состояния.
4. **Репозиторий → индекс → первый коммит.** Создать следующие полные разделы в явном порядке, покрыть status/diff/add/staged diff/commit разными ситуациями; убрать Git-вопросы из теста про терминал. Не менять старые ID и историю миграций.
5. **История, безопасное исправление, ветки и конфликт.** Отдельно добавить прочтение вывода и один симулятор конфликта; `diagnose-fix` включать только после проверки семантики и опасных вариантов. Проверить, что review не вознаграждает показанное решение.
6. **Remote, GitHub/PR и итоговая работа.** Сначала fetch/pull/push, потом UI PR, README и `.gitignore`; добавить связанный сценарий из нескольких шагов без запуска команд. Бонусы Figma/VS Code подключить боковыми ссылками на исходные `b1/b2` и их текущие progress records.
7. **Финальный аудит.** Проверить путь старых сохранений и ошибок, ручное чтение/сохранение совместимой облачной копии без автоматического восстановления, валидатор всех новых типов, доступность, 360/768/1280 px, темы, reduced-motion и честность результата теста. Проверки выполнять на изолированных фикстурах.

Первый содержательный релиз — один завершённый раздел, его контроль и одна новая форма чтения вывода. Следующие разделы добавляются только после прохождения полного цикла «объяснение → практика → проверка → повтор ошибки → совместимое сохранение», а не как пачка пустых карточек.

## Реализация первого раздела

Добавлен `terminal-paths-v1` с неизменяемыми ID узлов `course-terminal-study`, `course-terminal-practice` и `course-terminal-check`. Он хранится отдельно от legacy-уроков `1..5`; старые результаты не дают автоматического зачёта нового материала. Первый раздел рассчитан на Git Bash для Windows: 10 тренировочных вопросов, связанная трёхшаговая учебная практика и 5 контрольных вопросов (проходной порог проекта — 4 из 5). Повтор практики после первого зачёта свободный и не выдаёт XP повторно; тестовый бонус выдаётся только при первом сохранённом зачёте.

`output-reading` включён в практику, контроль и review. В исходном примере плана тип проверял вывод `git status` и поля индекса/рабочего дерева, которых раздел терминала ещё не объясняет. Для первого раздела применена та же схема безопасного разбора вывода и явных записей, но записи имеют вид `{path, kind}` (`file`, `directory`, `current-directory`); команда, среда, сырой учебный вывод, варианты и структурированный ожидаемый ответ остаются отдельными полями. Команды моделируются и никогда не запускаются в браузере. Для последующих разделов валидатор сможет расширить whitelist полей этого типа отдельной совместимой правкой.

Состояние `courseProgress` необязательно в v1. Старые локальные и облачные снимки без него остаются валидными; оно добавляется при первом подтверждённом завершении узла, без миграции и без переноса legacy-достижений. В review новый вопрос адресуется стабильным `task.id`, а не индексом массива.

Остались следующие этапы: подсказки, зависящие от уровня знаний; компактный статус этапа вместо постоянной полосы; полноценные следующие разделы и граф карты; новые типы заданий `diagnose-fix`/`sequence`; дальнейшее расширение интерпретации `output-reading` для Git-вывода. В этом этапе геометрия карты и помощь по уровню не менялись.
