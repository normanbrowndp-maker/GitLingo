# Подготовка Supabase для будущих аккаунтов

Этап подготавливает только схему базы и правила доступа. Приложение не подключено к Supabase: гостевой режим и локальный `mega-state` продолжают работать как раньше. Миграция ничего не переносит из браузера и не создаёт пользователей.

## Что хранится

Миграция `supabase/migrations/20261027090000_prepare_accounts.sql` создаёт:

- `public.profiles`: `id` — UUID и FK на `auth.users(id)` с каскадным удалением; `display_name` — обрезанное по краям отображаемое имя длиной 1–40 символов; `created_at`, `updated_at`.
- `public.user_progress`: `user_id` — UUID и FK на `auth.users(id)`; `state` — один JSONB-снимок локального состояния; `schema_version` — версия формата (`1` соответствует `v: 1` в [STORAGE.md](STORAGE.md)); `revision` — серверная целочисленная ревизия; временные метки.

`state` — только объект, его `v` должен совпадать с `schema_version`. При будущей сериализации передавать нужно только содержимое `progress` из `MEGA.state.exportProgress()`, а не всю экспортную оболочку. Тема, `mega-last-result` и ключ локальной копии `mega-state-backup-v1` в облачное поле `state` не входят.

Эта проверка структуры не защищает от накрутки XP: клиент контролирует содержимое JSON и может отправить поддельный прогресс. На следующем этапе это всё ещё будет клиентское состояние; данная схема не является серверной проверкой игровых наград.

## Подготовка отдельного проекта

1. Создайте отдельный Supabase-проект для GitLingo. На этом этапе не нужно создавать платные дополнения или подключать сайт.
2. Перед применением миграции проверьте, не заняты ли имена `public.profiles`, `public.user_progress`, функций `public.touch_profile_updated_at()` и `public.touch_progress_metadata()`, одноимённых триггеров и политик. Проверьте их столбцы, ограничения, владельцев, grants, RLS и зависимости. Миграция намеренно использует обычный `CREATE`, а не `IF NOT EXISTS`: существующий объект не считается совместимым автоматически. Если имя занято, сначала вручную сравните схему и подготовьте отдельное согласованное изменение; не удаляйте и не переименовывайте существующую таблицу наугад.
3. Примените SQL-файл один раз через миграционный процесс Supabase или SQL Editor отдельного тестового проекта. Не выполняйте его в существующей production-базе без предварительной проверки схемы и резервного плана.
4. Запустите проверки из [`supabase/tests/access_checks.sql`](supabase/tests/access_checks.sql), затем пройдите клиентский сценарий из [`supabase/tests/README.md`](supabase/tests/README.md). SQL Editor с административной ролью сам по себе не проверяет доступ обычного пользователя.
5. В Authentication включите регистрацию по email и паролю и оставьте включённым подтверждение email. Настройте шаблон письма и доставку по требованиям проекта. У hosted Supabase подтверждение включено по умолчанию, но проверьте настройку явно.
6. В Authentication → URL Configuration укажите Site URL и точные разрешённые Redirect URLs перед тестированием писем. Для localhost используйте конкретный адрес и порт вашего локального сервера, например `http://localhost:PORT/` после выбора порта. Для production сначала подтвердите реальный GitHub Pages URL в настройках репозитория и добавьте его как HTTPS URL. Адрес Pages в репозитории не закреплён, поэтому здесь оставлен плейсхолдер: `<ПОДТВЕРЖДЁННЫЙ_HTTPS_URL_GITHUB_PAGES>`.
7. Не добавляйте широкий wildcard redirect для production без конкретной необходимости. Redirect URL должен соответствовать назначению приложения; Site URL используется как адрес по умолчанию для подтверждений и восстановления доступа.

Гостевой режим остаётся доступен через `file://`, так как сайт не делает запросов к Supabase. Аккаунты нельзя полноценно проверять через `file://`: для Auth используйте localhost с согласованными адресом и портом. Опубликованный сайт должен работать по HTTPS.

## Ключи и секреты

Публичный `publishable`-ключ (`sb_publishable_...`; прежний `anon` — legacy-вариант) предназначен для браузера, поскольку он виден посетителям. Сам по себе он не подтверждает пользователя и не заменяет RLS. Доступ определяют JWT авторизованного пользователя, grants и политики.

`secret` (`sb_secret_...`) и legacy `service_role` обходят RLS и должны оставаться только в доверенной серверной среде. Пароль базы также секретный. Ни один из них нельзя помещать в HTML, JS, SQL-тесты, документацию или Git. Простое помещение секрета в `config.js` или `.env` не помогает, если значение затем отправляется в браузер. Не присылайте секреты в чат.

Эти названия и свойства ключей могут меняться; перед следующим этапом сверяйтесь с текущей [официальной документацией Supabase по API keys](https://supabase.com/docs/guides/getting-started/api-keys). В этой версии приложения нет ни ключей, ни клиентской библиотеки, ни сетевого подключения.

## RLS, время и конфликты обновления

RLS включён на обеих таблицах. Для `authenticated` каждая операция ограничена `auth.uid()` и владельцем строки: `profiles.id` либо `user_progress.user_id`. Для `anon` табличные права отозваны. UPDATE также ограничен grants на столбцы: профиль можно менять только в `display_name`; прогресс — в `state` и `schema_version`. Владелец, `created_at`, `updated_at` и `revision` не доступны для клиентского изменения. `BEFORE`-триггеры без `SECURITY DEFINER` выставляют время, сохраняют исходный `created_at`, устанавливают начальную `revision = 1` и увеличивают её на каждом UPDATE.

Страница аккаунта читает только строку текущего пользователя. Ручное сохранение сначала показывает локальную и облачную сводки, затем обновляет запись с фильтрами `user_id = текущий пользователь` и `revision = показанное значение`. Условное обновление с устаревшей ревизией затронет ноль строк: интерфейс перечитает копию и запросит новое подтверждение. При отсутствии строки выполняется явный INSERT без upsert. Облачная запись не загружается в игру.

Строки `profiles` и `user_progress` не создаются автоматически при регистрации. Отсутствующая строка `profiles` создаётся по кнопке сохранения профиля; строка `user_progress` — только после отдельного подтверждения первой облачной копии. Триггеров на `auth.users` и функций с повышенными правами миграция не создаёт.

## Бэкапы

Git хранит исходный код и миграции, но не копию пользовательских аккаунтов или облачных данных. Локальная копия `mega-state-backup-v1` хранится в браузере и не является резервной копией Supabase. Наличие и срок хранения автоматических резервных копий зависит от текущего плана и настроек Supabase; после создания проекта отдельно проверьте доступные средства восстановления и проведите пробное восстановление в отдельном проекте. Не выполняйте восстановление прямо в рабочую базу без проверки последствий.

Клиентское состояние XP не защищено от накрутки и не является подтверждением наград. Облачная копия служит ручной копией данных, а не резервной копией базы; отдельно проверьте настройки резервного копирования Supabase.

Полезные страницы официальной документации: [RLS и grants](https://supabase.com/docs/guides/database/postgres/row-level-security), [парольная Auth](https://supabase.com/docs/guides/auth/passwords), [Redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls), [резервные копии](https://supabase.com/docs/guides/platform/backups).
